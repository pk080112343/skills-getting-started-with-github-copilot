###############################################################################
# 1. Product overview
###############################################################################
#
# Product name:
#   Mergington High School Activities API
#
# Purpose:
#   Provide a simple web application where students can browse extracurricular
#   activities, register for an activity, and unregister when needed.
#
# Audience:
#   Mergington High School students and staff using the activity directory.
#
# Current architecture:
#   A FastAPI backend serves JSON endpoints and a static HTML/CSS/JavaScript
#   frontend. Activity data is stored in memory in src/app.py.
#
# Persistence:
#   There is currently no database. All participant changes are lost when the
#   server restarts.

# 3. API contract
###############################################################################
#
# GET /activities
#   Returns all activities, including descriptions, schedules, participant
#   limits, and current participant email lists.
#
# POST /activities/{activity_name}/signup?email=<email>
#   Registers an email for an existing activity.
#   Returns 200 on success, 400 for duplicate signup, and 404 when the
#   activity does not exist.
#
# DELETE /activities/{activity_name}/unregister?email=<email>
#   Removes an existing participant.
#   Returns 200 on success, 404 when the activity or participant is missing.

###############################################################################
# 4. Data model and application logic
###############################################################################
#
# Activities are represented by an in-memory Python dictionary:
#
#   activity name
#     - description: activity summary
#     - schedule: meeting time
#     - max_participants: enrollment capacity
#     - participants: list of student email addresses
#
# Signup logic:
#   1. Validate that the activity exists.
#   2. Validate that the email is not already registered.
#   3. Append the email to the participant list.
#
# Unregister logic:
#   1. Validate that the activity exists.
#   2. Validate that the email is registered.
#   3. Remove the email from the participant list.
#
# Frontend logic:
#   1. Fetch activity data from GET /activities.
#   2. Render an activity card for each activity.
#   3. Submit signup requests from the form.
#   4. Submit unregister requests from each participant's trash button.
#   5. Re-fetch activities after a successful mutation so the UI stays current.
